# Phase 16: Alpha Decay Monitoring System - Context

**Gathered:** 2026-04-25
**Status:** Completed (Auto-selected recommended options)

<domain>
## Phase Boundary

Implement a live health monitoring system for signal families. As live market conditions change and alpha decays, this system automatically tracks performance against backtest baselines and actively throttles (or pauses) conviction weights in the combination engine to prevent catastrophic drawdown.
</domain>

<decisions>
## Implementation Decisions

### Baseline Retrieval Mechanism
- **D-01:** JSON Baseline Manifests. The live monitor does not recalculate baselines on the fly. It reads a static `baseline.json` file generated by the Backtesting Engine (Phase 15). This JSON contains the ground-truth expected Hit Rate, Average R, and baseline Sharpe for exact statistical deviation checks.

### Automatic Weight Reduction Mechanism
- **D-02:** Dynamic Health Multipliers. When a signal family experiences alpha decay (e.g., 30-day Sharpe < 0), the Decay Monitor updates an in-memory `health_multiplier` (e.g., changing it from 1.0 to 0.5). The Signal Combination Engine multiplies its Softmax output by this `health_multiplier`, instantly reducing the capital allocation by 50% without altering config files.

### The "Pause" Mechanism
- **D-03:** Multiplier Zeroing. If catastrophic decay is detected (e.g., Average R < 0.5R or a > 2σ deviation in hit rate), the monitor drops the `health_multiplier` to `0.0`. This gracefully pauses the signal family—its signals are still generated and evaluated in the background for recovery analysis, but they carry exactly zero conviction weight and generate zero trades.
</decisions>
